wrf_gpu User's Guide

A GPU-native, WRF-compatible regional weather model · v0.23.1

wrf_gpu runs a standalone WRF v4 ARW forecast end-to-end on a single GPU. It reads a standard WRF namelist.input, initializes from WRF real-data artifacts (wrfinput_* and wrfbdy_d01; no CPU-WRF wrfout dependency), integrates a nonhydrostatic split-explicit ARW dynamical core on the GPU, and writes a WRF-compatible wrfout history file.

Built on the shoulders of WRF. This project is an independent, AI-written re-implementation of the same physics solver, GPU-optimized and validated cell-for-cell against WRF as the result oracle. It is not a port of the WRF Fortran source and is not affiliated with or endorsed by UCAR/NCAR. The Weather Research and Forecasting (WRF) model is developed and maintained by NCAR/UCAR and the WRF community; please cite and credit them. See Credits, License & Citation.
Read this first — what this software is

wrf_gpu is a transparent research artifact: a clean JAX rewrite whose dynamics/thermodynamics core is proven cell-for-cell identical to CPU-WRF v4 over 72 h. It is honest about its edges — the broader 24–72 h forecast-skill equivalence is an open credibility gate, not yet claimed closed. Priority order, in every design decision: stability > identity > speed > memory. There is no masking, clamping, or nan_to_num anywhere on the result path.

✨ New — run it by just asking an AI

Clone the repo, open an AI coding agent (Claude Code / Codex / OpenCode), and say "here is my input, get it running." The repo ships an operator skill the agent auto-loads — it sets up the environment, checks your GPU, smoke-tests, and runs your case, narrating each step and its ETA. What it is good for¶

  • Running real regional ARW forecasts on a GPU from a standard WRF namelist — single-domain or live-nested (d01→d02→d03, down to a 1 km nest), with native init, restart, and a WRF-compatible wrfout.
  • Capability the CPU stack cannot reach on one box. A 1 km single domain fits one RTX 5090 bit-identically, and the all-7-island 1 km nested case runs end-to-end on one card.
  • Throughput at scale and on many cases. The GPU advantage grows with grid size; the opt-in batched ensemble fills an otherwise-idle small-grid GPU by running many same-geometry cases at once.
  • A forkable, auditable artifact. Every claim has a proof object on disk; every architecture decision has a cross-model-reviewed ADR.

What it is NOT¶

  • Not a universal WRF v4. It covers the common operational ARW subset (the wired physics menu). Every unsupported namelist option fails closed before any compute with a named reason — it never silently substitutes a scheme. See Namelist Compatibility.
  • Not proven for full 24 h/72 h forecast-skill equivalence. The dynamics/thermodynamics core is cell-for-cell identical to CPU-WRF; broader T2/U10/V10 skill equivalence is the open gate (details).
  • Not a blanket single-card speedup. On tiny geometries the GPU can be launch/occupancy-bound and slower than multi-rank CPU-WRF; the advantage grows with scale.
  • Not WPS/real.exe, DFI, FDDA/nudging, WRF-Chem, WRF-Fire, urban (BEP/BEM) or lake. See Boundaries & Known Issues.

New to the workflow?

If you already run WRF, the biggest change is that wrf_gpu replaces wrf.exe with a single command, python -m gpuwrf.cli run, and initializes from the same wrfinput_*/wrfbdy_d01 artifacts a WRF real-data case already uses. Keep your namelist.input and current preprocessing chain for producing those artifacts. Start with the Quickstart, then read Input Data & Initialization.
