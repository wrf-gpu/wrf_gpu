Performance, memory and energy

Whole-run speed and energy figures below retain their measured v0.3.2 windows; the v0.3.3 science wave is not a new quiet-host throughput benchmark. The v0.3.3 small-grid stability firewall adds about 12% kernels and 8% ordinary-root time on grids of ≤4096 horizontal columns only. Large WN3/Monica programs are byte-identical across that firewall delta.

Use the measured hardware, workload and clock behind each number. This page keeps v0.3.2 benchmarks dated; completed v0.3.3 trajectory and compiled-program evidence is linked on the validation page. Older timings are not relabelled as new W3 measurements.

Large regional forecasts on one card¶

[M] RTX 5090 (sm_120, CUDA 13), Ryzen 9 9950X: a cached 24-hour Canary 9/3 km two-domain run takes 79.319 seconds total, 3.305 s/forecast hour, including startup and output. The twelve-core original CPU-WRF main-loop reference is 92.3 s/hour: a 27.9× clock ratio. CPU and GPU windows are explicitly different. The host was contended; this is a conservative measured absolute result, not a quiet-host or universal speed claim.

The matched v0.3.1 GPU run took 88.060 seconds, 3.669 s/hour; B/A=0.901, 9.9% lower whole-run wall [M]. The v0.3.2 steady-segment median is 2.625 s/hour, and initialization/pre-step work is 15.008 seconds. Small grids can remain launch-limited; that does not negate the measured regional single-card gain.

The first run compiles¶

A new source, geometry or target can spend minutes compiling before integration. Cold setup is a separate cost from a warm forecast. Run a new geometry/version alone once before attempting concurrent cold builds. No quiet-host W3 compile or warm-readiness number is inferred from the old benchmark.

Reuse compatible executables¶

Later compatible runs reuse caches. Native nested AOT prefetch defaults ON; OFF loads at first dispatch. Compatibility includes target and effective controls. A copied cache can safely refuse a fingerprint mismatch even when pin-file contents match: path-bearing XLA flags are part of the target binding. Refusal is not a forecast failure or permission to bypass compatibility checks.

Independent cases sharing one GPU¶

[M] Four three-nest Tenerife cases × 24 h measured 5.507 s/case-hour aggregate, 22.4× the CPU-WRF 3×4-core main-loop throughput reference (123.4 s/case-hour). The all-four-running steady window measured 4.857 s/case-hour, 25.4×. Whole-run clocks include init/load and output, without compression. The FIFO tail is not the steady-window throughput number. Greater aggregate throughput can increase one case's latency.

Different dates or members¶

scripts/run_parallel_cases.sh --out-root runs/batch CASE_A CASE_B -- \
  --domains-from-namelist --hours 24

The launcher checks both GPU and host memory, admits cases and queues the rest. v0.3.2 observed 5,032 MiB warm GPU allocation/case and about 5.6 GB host high-water; these are workload-specific values, not universal sizing constants.

Precision with original-WRF evidence¶

Validated fp32 hot paths and carry are defaults on GPU, with WRF DOUBLE islands retained. Original-CPU comparisons cover selected regional 24/72-hour cases. An opt-out or different scheme combination needs its own scope; older f64 fallback still has the historical Eddington shortwave choice, while W3 REFTRA corrects the active REAL path. See validation.

C-auto and measured memory¶

Preflight priority is explicit GPUWRF_MIN_FREE_VRAM_GIB, then a verified geometry/settings C-auto plan, then cold fallback max(24 GiB, 0.50 × total VRAM). A reserved pool needs outside-pool headroom; an unreserved pool also needs its budget. Explicit allocator settings win. Cold compilation and warm forecasts have different host peaks.

Measured board energy and inferred scenarios¶

[M] The v0.3.2 four-case sweep integrated timestamped board-power samples to 0.678 Wh/case-hour. Adding an assumed 67 W host share gives 0.780 Wh [I]. The twelve-core CPU reference uses approximately 200 W, maintainer measurement; its energy is 6.86 Wh/case-hour [I]. This accounting is not measured whole-machine efficiency. Four-core Swiss CPU energy is unknown.

Existing ensemble/giant-domain scenarios on H100/B200/B300 are inferred, not data-centre GPU runs. Distributed multi-GPU forecasts are not implemented. See the methods, assumptions and uncertainty.
