Performance & GPU Modes

wrf_gpu's value is capability, fidelity, stability and energy efficiency at scale — not a blanket single-card speedup. This page explains the one-time compile and the seconds-fast warm start, the opt-in throughput modes, VRAM sizing, and exactly which performance claims are measured versus projected.

v0.23.4 candidate: d03 performance regression measured, root-caused, not fixed

A dispatch-level fix leaves 2-domain (d01+d02) performance unaffected (measured 0.960–1.018× v0.23.3), but the production-faithful maxdom3 canary measures 51.67% slower (1.9668543059 → 2.9831176877 s/root-step). 79.95% of the added cost is inside the FCT flux-limiter kernel's flux-renormalization computation. Every quick-fix candidate (barrier, scan/map, register-pressure/fusion-disable, B1/B2/B3 scheduling, roll substitution) was falsified or rejected with evidence, and a Nsight Compute hardware measurement confirmed the kernel is occupancy/latency-bound, not bandwidth-bound (DRAM throughput 20.3% of peak, achieved occupancy 15.6%), ruling out a reduced-precision fix and identifying concurrent sibling-domain scheduling as the mechanistically-mapped next lever (design-scoped, not implemented). The investigation is closed; this regression ships as a known, understood limitation. The accepted all-physics nine-domain stress replay used 5,744.407 s warm model wall for one forecast hour, with 16,624 MiB peak VRAM and 35,773,432 kB peak host RSS. That stress workload proves correctness and capacity, not cross-version performance.

The honest one-paragraph summary

On tiny single-domain grids the GPU is launch/occupancy-bound and can be slower than multi-rank CPU-WRF (~2.3× slower at 129²). The advantage grows with scale: the all-7-island 1 km nested fast path measures ~1.53× faster than same-box 12-rank CPU-WRF and is byte-identical to the prior release. Big multiples (≥2–3×) are not reachable on one card and fp32 does not change that. The scale levers are algorithmic + multi-GPU + batching, and are honestly labelled measured or projected below.

First run is slow on purpose — the cold compile¶

The first forecast JIT-compiles the GPU kernels: a one-time cold compile with no output before integration starts. It is compiling, not hung. Compile time scales with grid size:

CaseOne-time cold compile
Bundled single-domain d01 (3 km)~½–2 min
Ordinary nested case~8–12 min
All-7-island 9-domain nesttens of minutes (a separate, larger compile)

Warm cache & seconds-fast warm start¶

A persistent, per-user on-disk JIT cache is on by default with zero config. It is version-keyed (gpuwrf + JAX/JAXLIB + backend) so a stale older-release cache is never mistaken for a warm one, and it hits across forecast dates (a new or leap-year date is a warm hit — the date is a runtime argument, not baked into the program).

On the fused nested path, a fresh process then warm-loads the compiled GPU executable in seconds via an AOT cheap-key: the executable is serialized to disk and indexed by a metadata key computed without lowering, so a new process loads it directly and skips the multi-tens-of-minutes re-lower the old cache still paid.

Measured

The 9-nest fused stress re-confirm has both fused phases load source=aot_blob cross-process with 0 re-lower, all 9 domains finite (warm peak host RSS 16.4 GB); the 3-domain cold→warm gate is byte-identical to the cold compile (max_abs_diff 0) with no runtime regression. A warm load is numerically inert — the key only locates the blob.

Opt out with GPUWRF_NESTED_AOT=0; add the fail-closed backstop GPUWRF_AOT_VERIFY=1; use GPUWRF_BITWISE=1 or GPUWRF_NESTED_FUSE=0 for the eager bitwise/debug path. See Environment Variables.

Scope of the compile-cache win

The warm start is faster at getting a run started, not at running the forecast itself. Warm forecast throughput (seconds per forecast-hour) is unchanged from v0.20 and the default path is byte-identical — the warm start rides the same fused runtime executable, it just loads it from disk in seconds instead of re-lowering it.

Batched ensemble — filling the small-grid GPU (v0.23)¶

A single small operational nest under-uses the GPU: it is launch/occupancy-bound, so the card sits mostly idle. The opt-in batched ensemble runs B independent, same-geometry forecasts concurrently under one outer jax.vmap wrapped around the unbatched orchestration. The dynamical core is untouched; the default (GPUWRF_BATCH_ENSEMBLE unset / =1) is byte-identical.

Measured — Tenerife 3 km→1 km 2-nest, one RTX 5090, warm
B (concurrent cases)Total throughput% of large-grid ceilingPeak VRAM

The large-grid saturation ceiling is 5.81 M cells/s, measured on a compute-bound Alps 433²@1 km case on the same card. Batching the tiny Tenerife grid reaches ≈97 % of that ceiling at B=4. B_max=5 is VRAM-capped at ~26 GiB on the 5090; a larger card batches further.

Use it for many-case throughput — ensembles, parameter sweeps, parallel-in-time multi-day chunks — on small operational domains where one case leaves the GPU underused. Set the count with GPUWRF_BATCH_ENSEMBLE=4.

Distinct-init batches (same date, different ICs)¶

By default the batch replicates the single --input-dir across all B lanes. To batch distinct initial conditions — e.g. an initial-condition / perturbation ensemble for the same forecast date — list exactly B input directories in GPUWRF_BATCH_INPUT_DIRS (comma- or :-separated). The batched ensemble runs on the nested path (--max-dom > 1), one-way; every lane must be homogeneous — same grid, physics suite, timestep and forecast date/time — with only the initial/boundary data values differing.

Different forecast dates are not batchable (yet)

The date/time is baked into the namelist's static-aux (part of the compiled program's key), so lanes with different start dates fail closed with batch lane N d01: namelist/static treedef differs — even if only start_day/end_day differ. Batching stacks lanes under one jax.vmap, which needs one shared program; different dates compile to different programs. For multi-day throughput, run the days sequentially (each is its own warm-cache hit). True multi-date batching (threading the date as a per-lane runtime input) is a v0.24-and-beyond roadmap item.

# B=4 IC/perturbation members, SAME date, run concurrently
export GPUWRF_BATCH_ENSEMBLE=4
export GPUWRF_BATCH_INPUT_DIRS="/case/2025-01-21/mem1,/case/2025-01-21/mem2,/case/2025-01-21/mem3,/case/2025-01-21/mem4"
python -m gpuwrf.cli run \
    --input-dir   /case/2025-01-21/mem1 \
    --output-dir  runs/ic_ensemble \
    --max-dom     3 \
    --hours       24 \
    --scratch-dir /fast/nvme/scratch

Each lane writes its own wrfout set under --output-dir; the run payload records the resolved input_dirs and per-lane run_starts. Since v0.23.2 the separator accepts commas (the older :-only contract still works).

Does it fit in VRAM?

Batching stacks B lanes, so peak VRAM grows roughly with B. The win is on small, launch-bound grids that leave VRAM headroom (a Tenerife 3→1 km nest is ~9.4 GiB at B=1 → 18.3 GiB at B=4 on a 32 GiB card). A larger fp64 nest that already peaks in the ~20–30 GiB range does not leave room for B>1 on a 32 GiB card — there, run sequentially or use a bigger card.

Optional fp32 mixed-precision mode¶

The default path is pure fp64 and byte-identical. The opt-in GPUWRF_ACOUSTIC_PRECISION_MODE=mixed_perturb_fp32_v020 mode is capability/VRAM-only, not a speedup:

  • cuts whole-run VRAM by −14.4 % (aggressive mode) and extends full-physics cell capability ~1.16× (fits a 700² grid where fp64 caps near 650²);
  • on a single RTX 5090 it is not faster — the fp32/fp64 throughput-ceiling ratio is ≈0.91, and there is no peak-VRAM win on small single domains (radiation-transient-bounded below ~384²).
Honest scope of the fp32 fidelity check

fp32 tolerance bands are checked only at the 1 h forecast lead (19/19 fields green) — real, but not stringent (2–3 orders of magnitude inside the eventual 24 h skill bands). fp32 is only truly stressed by the 24–120 h skill gate, which is future work. fp32 is single-domain / capability-only: on the deep all-7 9-domain nest it can OOM on the RRTMG transient and is ~5× slower than fp64 there anyway. Do not read the 1 h pass as a 24–120 h skill proof.

VRAM & host memory sizing¶

CasePeak VRAM

Canary L2 d02 72 h nested gate≈ 29.8 GiB

Peak VRAM is transient working memory (radiation transients dominate), not persistent fp64 State. A --max-dom > 1 run performs a CPU-side VRAM-headroom preflight that fails closed (exit 75) before the long compile rather than OOMing mid-run; tune it with GPUWRF_MIN_FREE_VRAM_FRACTION / GPUWRF_MIN_FREE_VRAM_GIB or bypass with --force-gpu-run.

High resident host RAM (~36 GB)

A run currently holds ~36 GB of host RAM resident even at low VRAM, because the Noah-MP / physics constant tables are baked into the compiled executable rather than passed as runtime arguments. This is precision-independent and does not affect correctness or results, but it limits running two instances on a 64 GB box. Root-caused; the fix is deferred.

Default-path work reductions (v0.23)¶

v0.23 adds two value-preserving default-on reductions that cut work without changing results: P0 computes only the radiation flux slices the wrfout writer consumes (CPU bit-identical, 17/17 fields), and P3 fuses a flat 2-domain parent+child cascade into one program (fail-closed for every other topology, CPU sha256 fused==eager). The dynamical core is untouched (net dynamics diff vs v0.22.2 = 0 lines). The mandatory canary benchmark measures 407 vs 411 s/forecast-hour (3-domain, 1 h, warm) — no regression. See Validation → Default numerics.

Scaling & energy — measured vs projected¶

Measured

A real 1 km Alpine forecast runs on one professional GPU (full physics, convection-permitting). The device-bound fp64 kernel is near-roofline. The single-workstation energy-efficiency story is not yet an at-scale benchmark; per-kWh and cluster-level efficiency remain projected below.

Projected — not yet benchmarked at scale

This workstation has one physical RTX 5090. A multi-GPU shard_map + collective-halo (lax.ppermute) foundation exists and is bit-identity-validated on a fake/CPU mesh, and the scaling harness lifts to bigger GPUs — but real multi-GPU throughput, NVLink/NCCL bandwidth, and per-kWh figures at cluster scale are unmeasured and projected. No competitive benchmark (e.g. vs AceCAST) has been run; that positioning is an expectation, not a measurement.

Cross-version note: do not carry the historical ~674 s/forecast-hour number across topology, physics, and release boundaries. v0.23.4's nine-nest stress workload is materially different. Do not read the version history as a per-card nest-speed multiplier; use a matched canary or observed case progress.
