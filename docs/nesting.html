Nesting

wrf_gpu runs one-way live nesting — d01 → d02 → d03, down to a 1 km inner nest — entirely on the GPU. The parent domain advances and builds each child's lateral boundary live during the run, so you do not need a pre-supplied wrfbdy_d02. The child's initial condition comes from its own wrfinput_d0N; only wrfbdy_d01 forces the root. There is no CPU-WRF wrfout dependency.

How live nesting works¶

The nested driver is a standalone recursion faithful to WRF's module_integrate sub-cycling: the parent advances one step, constructs each child's lateral-boundary package from its own freshly-advanced state, and recurses into the child, which sub-cycles to catch up to the parent's clock. Each child's boundary update cadence is its parent's timestep. This is the validated one-way wiring (parent → child; the child does not modify the parent).

Grid and time sub-cycling ratios¶

The nest refinement is set by the WRF &domains key parent_grid_ratio (the spatial refinement, e.g. 3), read from the domain metadata. In this port parent_grid_ratio is both the spatial and the temporal sub-cycle ratio: a child takes parent_grid_ratio steps for every one parent step (WRF sub-cycling), which matches WRF's usual configuration where parent_time_step_ratio equals parent_grid_ratio.

Enabling a nested run¶

Nesting is opt-in via --max-dom N on gpuwrf run. With --max-dom 1 (the default) you get the single-domain path on --domain; with --max-dom N > 1 all domains d01..dN run together as the live-nested forecast.

python -m gpuwrf.cli run --input-dir my_case --output-dir runs/nested \
    --max-dom 3 --hours 24 --scratch-dir /fast/nvme/gpuwrf_scratch
A namelist max_dom is not auto-run

If your namelist declares max_dom > 1 but you omit --max-dom, the CLI runs a single domain (--domain) by default and prints a note telling you to pass --max-dom N to run the standalone live-nested forecast. Nesting is never entered implicitly. Remember the one-time cold compile on the first run (a large nested case can take several minutes) — later runs read the persistent JIT cache; see Running the Model and Performance.

Gravity-wave drag on nests¶

Orographic gravity-wave drag (gwd_opt=1) is default-ON on the nested 1 km path. Set GPUWRF_GWD_NESTED=0 to force it off for a memory-tighter config. See Dynamical Core.

Restart¶

Nested runs support the wrfrst-equivalent restart: the full per-domain physics carry is snapshotted and reloads bit-for-bit to continue the forecast. See Output Files.

Opt-in two-way feedback¶

Two-way nesting is opt-in via the --feedback flag (nested runs only). After each child finishes its sub-cycle, its interior is fed back onto the overlapping parent cells using WRF's copy_fcn area-average plus the sm121 feedback-zone smoother. The default is off (one-way nesting, the validated wiring).

Two-way equivalence is untested (KI-11)

The two-way feedback path is finite and stable, but its 24 h real-GPU equivalence versus CPU-WRF is untested. One-way live nesting is proven over a 24–72 h window; two-way is opt-in and not yet validated for equivalence. Use it deliberately.

Opt-in moving nests¶

An opt-in operational moving-nest driver is available. The static-nest path is byte-identical — enabling the moving-nest capability does not change results for a fixed nest. Vortex-following / adaptive-move configuration beyond this remains outside the validated operational default.
