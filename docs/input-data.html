Input Data & Initialization

wrf_gpu keeps the WRF run artifacts you already know: namelist.input, wrfinput_*, and wrfbdy_d01. It integrates those real-data inputs on the GPU with no CPU-WRF wrfout dependency, and auto-detects a legacy replay path when CPU-WRF wrfout history is present.

Usage parity with WRF

If you already run WRF, the biggest change is that wrf_gpu replaces wrf.exe with a single command, python -m gpuwrf.cli run. You keep your WRF real-data case directory and namelist.input; the supported namelist matrix runs as-is, and anything unsupported fails closed with a named reason.

Standalone native-init inputs¶

Operational The primary path is standalone native-init. The current CLI reads the model's initial state from wrfinput_<domain> and the root lateral-boundary forcing from wrfbdy_d01. There is no CPU-WRF wrfout replay in the loop; the forecast state is advanced by wrf_gpu on the GPU.

A standalone case directory looks like a normal WRF real-data case:

my_case/
├── namelist.input        # standard WRF v4 ARW namelist (bring your own)
├── wrfinput_d01          # initial state (one per domain you run)
├── wrfinput_d02
├── wrfbdy_d01            # lateral boundaries for the outer domain
└── met_em.d0*.*.nc       # met_em-stage forcing (metgrid output)

You produce these with any standard WRF preprocessing chain (WPS + real.exe) or use a bundled case that already contains them. For a live-nested run (--max-dom N) the parent builds each child's lateral boundary live, so you only need a per-domain wrfinput_d0N and wrfbdy_d01 for the outer domain — no pre-supplied wrfbdy_d02. See Nesting.

Replay mode (auto-detected)¶

Legacy path When the case directory already contains CPU-WRF wrfout history files (≥ 2 wrfout_<domain> files), run auto-detects replay mode: it takes the initial state and boundaries from that existing CPU-WRF history rather than building them natively. This is the validated skill-comparison harness — coupled-skill validation against CPU-WRF is run through it, not from a from-scratch native init.

Input dir contains…Detected modeInitial / boundary source
wrfinput_<domain> + wrfbdy_d01, no CPU wrfoutstandalone native-initIC from wrfinput, LBC from wrfbdy — built and integrated on the GPU, no CPU-WRF
≥ 2 CPU-WRF wrfout_<domain> filesCPU-WRF replayIC + LBC from the existing CPU-WRF wrfout history

Detection and the mode banner are described in Running the Model.

The role of namelist.input¶

Your namelist.input is the source of truth for the physics menu and many domain/output settings. The current CLI still uses a few explicit run-control flags, so it is not yet identical to wrf.exe's "just read the namelist" ergonomics. wrf_gpu reads the namelist directly:

  • It is validated fail-closed before any compute: an unsupported scheme is refused with a named reason, never silently substituted (see Namelist Compatibility).
  • &domains max_dom is read to know how many domains the case describes, but a nested run is opt-in via --max-dom — a multi-domain namelist run without --max-dom executes a single domain and prints a reminder.
  • Some cadence keys are approximated with a named, non-fatal warning: the cumulus / PBL cadence keys (cudt, bldt > 0) are not honored verbatim — the GPU port runs those physics every dynamics step (a conservative approximation), so a real WRF namelist (e.g. cudt=5) is accepted with a warning rather than rejected.

By default run uses <input-dir>/namelist.input; pass --namelist to point elsewhere.

Restart files¶

wrf_gpu supports the standard WRF restart mechanism — restart is bit-identity-validated, and the nested per-domain-subcycling path supports it too. Restart output cadence follows the usual namelist keys (restart, restart_interval). A restart file carries the WRF-faithful model state — including the 1 km inner-nest qke cold-start seed that the native init and the WRF-restart path both provide — so a restarted forecast resumes consistently.

What comes out¶

Initialization feeds the forecast, and the forecast writes a WRF-compatible wrfout NetCDF history file (plus a run-payload JSON) under --output-dir. Dimensions and variables match WRF's conventions; details and the variable subset are on the Output page.
