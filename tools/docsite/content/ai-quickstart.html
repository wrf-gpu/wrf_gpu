Quickstart with an AI Agent

wrf_gpu is designed to be driven by an AI coding agent. Clone the repo, open Claude Code / Codex / OpenCode (or any agent that reads a project's instruction files), and simply say: "Here is my input, this is what I need — get it running." The agent auto-loads an operator runbook that ships in the repo and does the rest, narrating each step.

Two front doors

This page is the human-facing explanation. The agent-facing instructions live in the repo as AI_OPERATOR.md and a Claude Code skill at .claude/skills/run-wrf-gpu/. You do not read those — your agent does. If you prefer to run the commands yourself, use the manual Quickstart instead.

How the AI-native quickstart works

The repository ships a small set of files that common agents load automatically when they open the checkout:

FileLoaded byRole
AI_OPERATOR.mdAny agent (referenced from the auto-load files)The authoritative end-user operator runbook the agent follows.
.claude/skills/run-wrf-gpu/Claude CodeA native skill that triggers when you ask to run/set up a forecast, and dispatches to the runbook.
AGENTS.md / CLAUDE.md bannerCodex, OpenCode, Claude Code, …A routing banner at the top that sends an agent helping an end user to AI_OPERATOR.md (the rest of those files is the port's internal dev protocol).

Because the instructions are in the repo, the agent gets accurate, version-matched knowledge of the real CLI, the required environment, the physics support matrix, and the honest limits — without you having to teach it.

Using it

# 1. Clone and open an AI coding agent in the checkout
git clone https://github.com/wrf-gpu/wrf_gpu.git && cd wrf_gpu
# open Claude Code / Codex / OpenCode here

# 2. Tell the agent, in your own words:
#    "Here is my case in ./my_case (namelist.input + wrfinput/wrfbdy).
#     Run a 24 h forecast and get me the wrfout. Set everything up."

The agent then works through the operator runbook and keeps you informed at every step.

What the agent does — and narrates

The runbook is an explicit, ordered playbook. A good agent will tell you what it is doing and how long each wait should take, roughly like this:

  1. Understand the request — detects your case directory, forecast length, single-domain vs nested (--max-dom), and output location.
  2. Environment — "creating a Python 3.11 venv, installing the CUDA build of JAX and the package…"
  3. GPU / driver check — "running nvidia-smi and jax.devices() to confirm the GPU is visible…"
  4. Smoke test — "running the bundled Switzerland 1-hour case first to prove the toolchain before touching your data…"
  5. Prepare your case — "setting GPUWRF_WRF_ROOT for the physics tables; validating your namelist (it fails closed on anything unsupported, with a named reason)…"
  6. Run & narrate — "JAX is compiling the GPU kernels — for this grid that's a one-time ~N minutes with no output, it's compiling, not hung… now integrating at ~X s per forecast-hour, so ~Y minutes for your 24 h run…"
  7. Deliver & verify — "your wrfout is in runs/…; here's the ncdump -h header."
Time estimates the agent will quote

The first run of a new grid or version includes a one-time compile: the bundled Swiss single-domain example took 380 s for its cold 24 h run versus 26 s warm (grid-dependent; nested cases compile longer). Later runs hit the warm cache. Warm throughput on an RTX 5090 is a few seconds per forecast hour for the two-domain Canary case (4.12 s; grid-dependent) — the agent refines the ETA from observed progress.
