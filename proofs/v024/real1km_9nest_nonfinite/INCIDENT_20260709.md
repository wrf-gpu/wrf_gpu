# real1km 9-nest d03/Ni incident (2026-07-09)

## Gate verdict

`HOLD / NOT_READY` for an 18-hour production or training-corpus
`real1km_9nest` GPU run. Two of two v0.23.3 runs failed in the same state leaf,
domain, level, and late-forecast window:

| cycle | failure | last complete d03-d09 group |
|---|---|---|
| `20250228_18z` | `d03 Ni k=0 step=9600 sim=57600 s index=(0,17,15)` | 15:40 |
| `20260706_18z` | `d03 Ni k=0 step=10000 sim=60000 s index=(0,24,21)` | 16:20 |

Both used the released v0.23.3 source (`07f4765e`), `mp_physics=8`, the same
9-nest geometry, `GPUWRF_NESTED_FUSE=0`, AOT, `cuda_async`, and the native
`d03` timestep of 6 seconds. The second run used full synchronous output; the
first used training-subset asynchronous output. The repeated failure therefore
crosses forecast date, full/subset output, and synchronous/asynchronous output.

## Decisive observations

1. The failing cells are open ocean in the southwest of d03, not steep terrain:
   - 20250228: 28.118866 N, -16.961426 E, `HGT=0`, `LANDMASK=0`.
   - 20260706: 28.182114 N, -16.900452 E, `HGT=0`, `LANDMASK=0`.
2. The retained full-output GPU run (`20260706`) has `QNICE=0` and `QICE=0`
   over every d03 cell and level at every written frame through 16:20. At the
   reported failure cell the entire hydrometeor column is also clear at 16:20.
3. The same-cycle CPU-WRF oracle is retained under
   `<DATA_ROOT>/alisios/runs/20260706_18z/real1km_killed_1100/real1km_9nest_case`.
   It is finite through 18:00. At 16:00, 16:20, 16:40, 17:00, and 18:00 its
   d03 `QNICE` and `QICE` fields are identically zero over the full domain.
4. The GPU state immediately before failure is otherwise finite at the reported
   cell. At 16:20 it has `QVAPOR=0.0156241255`, `T=-2.49304199` WRF perturbation
   theta, `P=1729.2604 Pa`, and `PB=99706.2031 Pa`; none is an extreme or
   non-finite precursor.
5. Nested production forces fp64 state. The old supercritical-step/steep-terrain
   explanation in `proofs/v022/nest_dycore` does not apply: this grid uses the
   native 6-second child timestep and the failures occur over ocean.
6. The output-boundary finite guard localizes the first bad *field in guard
   order*, not the first bad operation or timestep. It cannot prove that the
   Thompson source stage, sedimentation, physics-delta merge, child boundary
   handling, or AOT call first created the NaN.

## Current classification

`REPRODUCIBLE_GPU_PORT_STATE_TRANSITION_BUG`, exact operation not yet localized.
It is not case-specific and is not caused by history I/O, output subset, async
output, terrain, or a supercritical timestep. CPU-WRF truth excludes an expected
meteorological `Ni` failure. The repeated late-onset, clear-column shape is
consistent with either:

- an inactive-path NaN inside Thompson that survives when transient `qi` becomes
  active between output frames; or
- a per-domain AOT/runtime-lifetime or physics-delta transition that corrupts
  `Ni` after many segmented calls.

The prepared-runtime patch is not deployed and did not cause either failure. It
is a useful A/B falsifier because it removes repeated per-segment executable
deserialization, but it is not yet a correctness fix.

## Fastest settling diagnostic

1. Add an opt-in, on-device first-onset record to the d03 step scan. Carry one
   boolean plus first step/index and stage flags for `Ni`: step entry, Thompson
   output, post physics-delta merge, and post child-boundary application. Do not
   repair, clip, or transfer full state inside the timestep loop.
2. Reconstruct a diagnostic continuation from the retained 20260706 full
   16:20 d01-d09 frames if restart-equivalence can be proven. Otherwise rerun the
   retained case with the onset record. A continuation that is not restart-exact
   is evidence only, not a gate.
3. Once onset is reproducible, compare byte-identical inputs through:
   - released per-segment AOT runtime;
   - prepared-runtime reuse with the same AOT blobs;
   - JIT for the localized d03 interval, only in a conflict-free window.
4. Fix only the first divergent operation against WRF source/oracle behavior.
   A generic finite replacement or `Ni=0` clamp is prohibited.

## Release and tonight decision

- Do not deploy the prepared-runtime performance patch from CPU tests alone.
- Do not promote partial GPU outputs to the corpus.
- CPU-WRF remains authoritative for product/downscale generation.
- If an 18-hour GPU run is launched before localization, it is diagnostic and
  nonblocking only, with the finite guard enabled and automatic corpus rejection.
- The minimum correctness gate for a candidate is both retained cases finite
  through 18 hours, exact required subset presence, and CPU/GPU D0/grid/range/
  finite/pair QA. A three-hour performance A/B is no longer sufficient for
  deployment.
